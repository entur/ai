# MCP and LLM Backends

Use this reference for services in which a model retrieves untrusted content,
invokes tools, chooses arguments, or can cause an external action. Treat model
output as attacker-influenced even when the model or prompt is trusted.

## Identity, authority, and confused deputies

- Determine whether each operation intentionally uses caller-delegated identity,
  a workload identity, or a brokered capability. Service identity is not
  inherently wrong, but it needs explicit authorisation and narrowly scoped IAM.
- Bind user, tenant, audience, tool, and target resource at the enforcement point.
  Missing or invalid caller context must fail closed and must never fall back to
  a more privileged identity.
- Make read-only claims testable across every registered tool. Mutating tools need
  explicit scope, validation, auditability, idempotency where appropriate, and a
  user confirmation or approval boundary proportionate to impact.
- Sign or server-store opaque identifiers, cursors, approval tokens, and feedback
  IDs when a client could alter identity, subject, scope, or target fields. Bind
  them to the subject and expiry when replay or cross-user substitution matters.

## Prompt injection and untrusted content

- Trace direct user instructions and indirect instructions from documents, web
  pages, logs, tickets, repositories, tool results, images, and retrieved chunks.
- Separating system and user roles, labelling content as data, and sanitising
  obvious markup reduce confusion but do not reliably eliminate prompt
  injection. Do not report those measures as a complete control.
- Limit the model's available data and actions, keep deterministic policy checks
  outside the model, validate tool arguments and outputs, and require approval
  before high-impact or irreversible actions.
- Prevent untrusted content from choosing credentials, destinations, permissions,
  executable expressions, follow-up tools, or data returned to another subject.
- Test stored and multi-turn attacks, malicious tool descriptions, retrieved
  content that requests exfiltration, and instructions encoded in alternate
  formats.

## Tool execution and resource bounds

- Treat model-produced SQL, shell, paths, URLs, templates, JSONPath, `jq`, CEL,
  and API filters as untrusted input. Prefer structured constrained operations;
  otherwise sandbox the interpreter and disable file, environment, module, and
  network access that the feature does not need.
- Bound CPU, memory, recursion, fan-out, retries, result count, and encoded output
  size before large values are materialised. Post-hoc truncation does not prevent
  an out-of-memory failure.
- Rate-limit by authenticated subject and costly operation, not only by IP. Bound
  server-side limiter state even when keys are attacker-controlled.
- Validate every tool response before it re-enters the model or crosses a trust
  boundary. Ensure errors do not leak credentials, hidden prompts, other users'
  content, or privileged system details.

## Data isolation and observability

- Enforce tenant and document permissions during retrieval and again before
  returning content. Metadata filters generated by the model are not an
  authorisation boundary.
- Separate prompts, caches, vector indexes, conversation state, and evaluation
  data by subject and tenant where required. Verify deletion and retention across
  derived artifacts.
- Avoid recording full prompts, model responses, retrieved passages, and tool
  arguments by default. Trace and audit security-relevant decisions with
  redaction and access controls.
